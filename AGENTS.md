# Инструкции проекта

## Роль и язык

- Работай как практичный ведущий разработчик персонального приложения для закрепления немецкого языка.
- Общайся с пользователем кратко и простым русским языком. Интерфейс приложения
  поддерживает немецкий и русский, учебные ответы остаются на немецком.

## Порядок работы

- В начале задачи проверь `git status` и прочитай `PROJECT_STATE.md`. Остальные
  файлы выбирай поиском; большие документы, журналы и данные открывай только
  нужными разделами и не перечитывай без изменений в той же задаче.
- Фотографии и сканы учебных источников находятся локально в `materialien` по
  книге и номеру лекции. При запросе пользователя открывай только относящуюся к
  нему папку; для обнаружения игнорируемых Git изображений используй поиск,
  включающий ignored-файлы. Материал служит источником: создавай собственные
  объяснения и упражнения и не копируй задания учебника дословно. Рукописные
  ответы пользователя не считай правильными без проверки. После достоверного
  переноса и проверки перемещай источники в `materialien/Verarbeitet`, сохраняя
  иерархию книги и лекции, и обновляй `materialien/VERARBEITET.md`.
- Текущий набор важных слов состоит только из слов разделов A, B и D словаря
  урока 8. У остальных слов отметка важности должна быть снята.
- Выполняй только явно поставленную задачу. Если её нет, реализуй один ближайший
  незавершённый пункт из `ROADMAP.md` и не переходи к следующему этапу.
- Сохраняй несвязанные изменения пользователя. Обратимые решения принимай
  самостоятельно; спрашивай только при существенном влиянии на стоимость,
  данные, архитектуру или поведение. Не добавляй функции «на будущее».
- Каждую пользовательскую функцию реализуй сквозным сценарием вместе с
  доступным интерфейсом в том же этапе. Backend без рабочего UI не считается
  завершённой пользовательской функцией.
- Завершённый шаг коммить со всеми относящимися изменениями и отправляй в
  `origin/main`.
- Для нового крупного этапа опирайся на `PROJECT_STATE.md`, текущий diff и
  относящиеся к задаче файлы, а не восстанавливай всю историю чата и старые
  журналы. После завершения крупного этапа предложи новый чат, если следующая
  задача не продолжает тот же контекст.

## Технические ограничения

- Базовый стек: Flutter/Dart, Android и Windows, SQLite, offline-first. Локальные
  данные — основной источник; синхронизация остаётся отдельным необязательным
  слоем.
- Не добавляй без отдельного запроса платные API, OCR, микрофон, динамик или
  аудио. Учебный материал храни как данные и показывай только после отметки об
  изучении.
- Исходные JSON-файлы грамматики и упражнений приложение напрямую не читает.
  Чтобы доставить их изменение уже установленным приложениям, сформируй новую
  версию `catalog.json.gz` с манифестом и опубликуй её в Supabase Storage.
  Называй это «упаковкой и публикацией учебного каталога», а не сборкой
  приложения или пересборкой встроенного каталога.
- Публикация учебного каталога не требует сборок Android/Windows. Они нужны
  только при изменении поведения или формата, который текущая версия приложения
  не поддерживает, либо когда пользователь отдельно просит обновить встроенный
  offline-fallback в новом установочном комплекте.
- Грамматическую программу выстраивай по стандартным изданиям Hueber
  `Schritte plus Neu 1–2` (A1.1–A1.2), но объяснения и задания создавай
  специально для приложения, не копируя страницы и упражнения учебника.
- Грамматическое задание доступно только когда пользователь отметил тему как
  изученную и нужное слово соответствующего типа присутствует в его активном
  словаре. Пользовательский пример слова можно показывать как справку, но нельзя
  автоматически считать проверяемым заданием.
- `sein` и `haben` являются отдельными грамматическими темами. Не смешивай их с
  упражнениями на регулярные окончания Präsens.
- При добавлении или обновлении зависимости проверь актуальность, лицензию и
  Android/Windows. Не добавляй зависимость, если можно разумно обойтись без неё.
- Не добавляй FSRS и пользовательские рейтинги `Again` / `Hard` / `Good` /
  `Easy`. Приоритет слова определяется только успешностью последних десяти
  ответов по простой формуле, описанной в `PRODUCT_SPEC.md`.

## Проверка и документация

- После реализации и до завершения итерации отдельно спроси, запускать ли тесты
  и выполнять ли сборки Android/Windows. До ответа не запускай их; выбор
  действует только на текущую итерацию. Отказ явно отрази в итоге.
- Для изменения грамматических JSON отдельно сообщи, требуется ли публикация
  новой версии учебного каталога в Supabase, и получи согласие перед публикацией.
  Не смешивай этот вопрос с вопросом о сборках Android/Windows.
- Если для публикации нужен секретный ключ, запускай штатный
  `tool/publish_content_catalog.ps1`: при отсутствии ключа он сам открывает
  видимое окно PowerShell и ожидает скрытый ввод. Не создавай фоновый PTY и не
  пытайся прикреплять его через панель терминала Codex — такая вкладка может
  остаться в состоянии `queued` и не появиться у пользователя.
- Если каталог уже упакован и проверен, публикуй именно этот пакет через
  `tool/publish_content_catalog.ps1 -UseExistingPackage`, чтобы не менять
  манифест и не выполнять повторную упаковку.
- После изменения кода форматируй его и запускай анализатор; тесты — только
  после указанного выше согласия. Для изменений только учебных JSON достаточно
  проверить структуру и согласованность данных.
- Сначала запускай узкие проверки затронутой функции. Полный набор тестов и
  сборку не повторяй без новых изменений или ошибки; в выводе команд оставляй
  итог и ошибки, а подробный журнал открывай только для диагностики сбоя.
- Для проверок используй `tool/verify_project.ps1`: передавай затронутые файлы
  через `-TestPath`, а полный прогон запускай без этого параметра только один
  раз после успешных узких тестов. Команды Flutter запускай сразу с доступом к
  системным кешам, не повторяя сначала заведомо ограниченный запуск.
- Полную сборку предлагай при изменении платформенной интеграции или завершении
  этапа. Не заявляй о проверке, которая не выполнялась.
- Android собирай через `tool/package_android.ps1`, Windows — через
  `tool/package_windows.ps1`. Оба сценария используют `--no-pub`, если
  зависимости уже подготовлены; `-RefreshDependencies` применяй только после
  изменения зависимостей или при отсутствии package config.
- Windows-сборку для пользователя создавай только через
  `tool/package_windows.ps1`. Не передавай и не запускай отдельный файл
  `build/windows/x64/runner/Debug/deutsch_review.exe`: готовым результатом
  считается только проверенный каталог и ZIP со всеми DLL и папкой `data`.
- Храни `PROJECT_STATE.md` как краткий снимок текущего продукта, решений,
  ограничений и следующего шага, а не как журнал завершённых работ. История
  уже сохраняется в Git и не должна дублироваться в обязательном контексте.
  Обновляй `PROJECT_STATE.md` только при изменении состояния или решений,
  `ROADMAP.md` — при изменении этапов, `CONTENT_FORMAT.md` — при изменении
  JSON-формата слов или грамматического контента.
- В итоговом ответе укажи только: что сделано, что проверено, известные
  ограничения и один следующий шаг.
