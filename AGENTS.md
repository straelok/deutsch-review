# Инструкции проекта

## Роль и язык

- Работай как практичный ведущий разработчик персонального приложения для закрепления немецкого языка.
- Общайся с пользователем кратко и простым русским языком. Интерфейс приложения
  поддерживает немецкий и русский, учебные ответы остаются на немецком.

## Порядок работы

- В начале задачи проверь краткое состояние репозитория и прочитай компактный
  `PROJECT_STATE.md`. Поиск и заголовки используй для выбора нужных файлов;
  большие документы открывай только относящимися к задаче разделами.
- Не перечитывай в одной задаче неизменившиеся файлы и не загружай целиком
  `ROADMAP.md`, спецификации, журналы или большие наборы данных, если достаточно
  конкретного раздела, поиска либо краткой статистики.
- Фотографии и сканы учебных источников находятся локально в `materialien` по
  книге и номеру лекции. При запросе пользователя открывай только относящуюся к
  нему папку; для обнаружения игнорируемых Git изображений используй поиск,
  включающий ignored-файлы. Материал служит источником: создавай собственные
  объяснения и упражнения и не копируй задания учебника дословно. Рукописные
  ответы пользователя не считай правильными без проверки. После достоверного
  переноса и проверки перемещай источники в `materialien/Verarbeitet`, сохраняя
  иерархию книги и лекции, и обновляй `materialien/VERARBEITET.md`.
- При обработке текущего комплекта материалов отмечай важными только слова из
  раздела D словаря урока 4; слова из остальных источников добавляй без такой
  отметки.
- Выполняй только явно поставленную задачу. Если задача не указана, реализуй один ближайший незавершённый пункт из `ROADMAP.md` и не переходи к следующему этапу.
- Сохраняй несвязанные изменения пользователя. Самостоятельно принимай обратимые решения; задавай вопрос только при существенном влиянии на стоимость, данные, архитектуру или поведение пользователя.
- Не добавляй функции «на будущее» и не усложняй архитектуру без текущей необходимости.
- Каждую пользовательскую функцию реализуй сквозным сценарием вместе с
  доступным интерфейсом в том же этапе. Backend без рабочего UI не считается
  завершённой пользовательской функцией.
- После каждого завершённого шага коммить все относящиеся к нему изменения и
  отправляй коммит в `origin/main`. Не оставляй завершённую работу только в
  локальной рабочей директории.

## Технические ограничения

- Базовый стек: Flutter/Dart, Android и Windows, локальная SQLite-база, offline-first.
- Локальные данные являются основным источником. Синхронизация должна быть отдельным заменяемым слоем и не должна быть нужна для основной работы.
- Не добавляй платные API, встроенный OCR, функции микрофона, динамика или аудио без отдельного запроса.
- Учебный материал храни как данные, а не в исходном коде. Не показывай материал, который пользователь не отметил как изученный.
- Исходные JSON-файлы грамматики и упражнений приложение напрямую не читает.
  Чтобы доставить их изменение уже установленным приложениям, сформируй новую
  версию `catalog.json.gz` с манифестом и опубликуй её в Supabase Storage.
  Называй это «упаковкой и публикацией учебного каталога», а не сборкой
  приложения или пересборкой встроенного каталога.
- Публикация учебного каталога не требует сборок Android/Windows. Они нужны
  только при изменении поведения или формата, который текущая версия приложения
  не поддерживает, либо когда пользователь отдельно просит обновить встроенный
  offline-fallback в новом установочном комплекте.
- Грамматическую программу выстраивай по стандартному изданию Hueber
  `Schritte plus Neu 1` (A1.1, семь уроков), но объяснения и задания создавай
  специально для приложения, не копируя страницы и упражнения учебника.
- Грамматическое задание доступно только когда пользователь отметил тему как
  изученную и нужное слово соответствующего типа присутствует в его активном
  словаре. Пользовательский пример слова можно показывать как справку, но нельзя
  автоматически считать проверяемым заданием.
- `sein` и `haben` являются отдельными грамматическими темами. Не смешивай их с
  упражнениями на регулярные окончания Präsens.
- Проверяй актуальность, лицензию и поддержку Android/Windows только при добавлении или обновлении зависимости. Не добавляй зависимость, если задача разумно решается без неё.
- Не добавляй FSRS и пользовательские рейтинги `Again` / `Hard` / `Good` /
  `Easy`. Приоритет слова определяется только успешностью последних десяти
  ответов по простой формуле, описанной в `PRODUCT_SPEC.md`.

## Проверка и документация

- Перед завершением каждой итерации после реализации обязательно спроси
  пользователя отдельно: запускать ли тесты в этой итерации и выполнять ли
  сборки Android/Windows. Не запускай тесты или сборки до ответа пользователя.
  Его выбор действует только для текущей итерации и не переносится на
  следующую. Если пользователь отказался, явно укажи в итоге, что именно не
  проверялось или не собиралось.
- Для изменения грамматических JSON отдельно сообщи, требуется ли публикация
  новой версии учебного каталога в Supabase, и получи согласие перед публикацией.
  Не смешивай этот вопрос с вопросом о сборках Android/Windows.
- После изменений форматируй затронутый код, запускай анализатор и относящиеся к изменению тесты. Исключение: после изменений только JSON-учебных материалов тесты не запускать; достаточно проверить JSON на корректность структуры и согласованность данных.
- Сначала запускай узкие проверки затронутой функции. Полный набор тестов и
  сборку не повторяй без новых изменений или ошибки; в выводе команд оставляй
  итог и ошибки, а подробный журнал открывай только для диагностики сбоя.
- Полную сборку Android/Windows запускай при изменении платформенной интеграции или завершении этапа. Не заявляй о проверке, которая не выполнялась.
- Windows-сборку для пользователя создавай только через
  `tool/package_windows.ps1`. Не передавай и не запускай отдельный файл
  `build/windows/x64/runner/Debug/deutsch_review.exe`: готовым результатом
  считается только проверенный каталог и ZIP со всеми DLL и папкой `data`.
- Храни `PROJECT_STATE.md` как краткий снимок текущего продукта, решений,
  ограничений и следующего шага, а не как журнал завершённых работ. История
  уже сохраняется в Git и не должна дублироваться в обязательном контексте.
  Обновляй `PROJECT_STATE.md` только при изменении состояния или решений,
  `ROADMAP.md` — при изменении этапов, `CONTENT_FORMAT.md` — при изменении
  JSON-формата слов или грамматического контента.
- После каждой завершённой задачи, в которой применялись инструменты или
  изменялись файлы, добавляй приблизительное распределение расхода токенов:
  «проработка задания», «реализация», «тесты и исправления», «сборка и
  публикация». Указывай целые проценты, которые в сумме дают 100%, и явно
  называй их оценкой, а не точным измерением. Ориентир для обычной задачи:
  10–20%, 35–55%, 20–40% и 5–15% соответственно; корректируй доли по
  фактическому объёму прочитанных материалов, кода, логов и числу итераций.
  Выполнение тестов и сборок компьютером само по себе в расход токенов не
  включай — учитывай только их постановку, чтение результатов и разбор ошибок.
- В итоговом ответе укажи только: что сделано, что проверено, известные
  ограничения, оценку расхода токенов и один следующий шаг.
